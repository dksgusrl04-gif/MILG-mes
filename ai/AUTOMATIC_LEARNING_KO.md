# MILG 기업별 자동 학습 · PoC 설치 운영

이 패키지는 고객 설비의 작업 데이터와 독립 검사 결과를 받으면, 지정한 공정·설비·품목·프로그램별로 후보 학습, 평가, 적용, 감시, 복구를 실행한다. 고객 데이터를 외부로 전송하거나 다른 기업의 모델·공통 배포 모델에 반영하지 않는다. 정상 기준 학습과 검사 합불 학습은 구분한다.

## 설치 담당자가 수행할 작업

1. Windows x64와 패키지 manifest에 기록된 Python major/minor를 준비한다. Python 설치 파일은 포함하지 않는다. ZIP을 고객별 새 디렉터리에 푼다. 패키지 원본은 신뢰된 MILG 배포본만 사용한다.
2. 최초 실행: `powershell -NoProfile -ExecutionPolicy Bypass -File .\Start-MilgDelivery.ps1 -InstallDependencies -Offline`. 가상환경·의존성·공개 모델·고객별 SQLite를 준비한다. 이후에는 `-InstallDependencies -Offline` 없이 실행한다. 시작 스크립트는 자동 점검 작업도 함께 실행한다.
3. `http://127.0.0.1:8765/operations`에서 토큰 두 개를 각각 입력한다. `runtime-state/pilot-token.txt`는 데이터/API용, `runtime-state/pilot-admin-token.txt`는 학습 정책·복구 관리자용이다. 관리자 토큰은 MES 위젯에 넣지 않는다. 토큰과 상태 폴더 접근권한은 고객 서버의 운영 계정·관리자로 제한한다.
4. 확인한 공정명·설비 ID·품목·프로그램/템플릿 버전을 등록하고 자동 학습을 활성화한다. `learning-policy.example.json`의 REPLACE 값을 실제 값으로 바꾼 후 시작 스크립트의 `-LearningPolicy "C:\MILG\customer-policy.json"`으로 등록할 수도 있다. 예시 이름으로 실데이터를 넣지 않는다. 데이터·검사 정의가 확정되지 않은 조건은 활성화하지 않는다.
5. 작업 입력과 검사 결과, LOT 종료를 연결한다. HTTP API 또는 아래 파일 수신 방식을 사용한다. 먼저 시연 데이터로 연결을 시험하고, 실제 독립 검사 데이터만 `demo:false`로 보낸다. 합불을 모델 예측으로 채우지 않는다.
6. 자동 실행을 등록할 경우 수동 서버를 종료하고, 관리자 PowerShell에서 `powershell -NoProfile -ExecutionPolicy Bypass -File .\Install-MilgStartup.ps1`을 실행한다. Windows 작업 스케줄러의 `MILG-Engine-PoC`가 Local Service 계정으로 부팅 시 실행하고 비정상 종료 시 재시도한다. 제거는 같은 스크립트의 `-Remove`로 한다. 설치 스크립트는 서비스 계정에 패키지 읽기·상태 폴더 수정 권한을 부여하며 상태 폴더 접근은 운영자·관리자·서비스 계정으로 제한한다. 기본 Python 실행 파일도 서비스 계정이 읽고 실행할 수 있어야 한다. 고객 PC의 부팅/권한 조건은 실제 설치 때 확인한다.
7. 원격 MES 브라우저가 접속한다면 고객망 HTTPS 역방향 프록시를 통해 연결한다. Python 서버는 127.0.0.1에만 바인딩한다. 프록시가 `/api/learning/configure`, `/api/learning/rollback`을 운영자에게만 열도록 구성한다. 시작 스크립트의 `-AllowedOrigins`에는 승인한 MES origin만 지정한다. 기본 Local Service 시작 작업은 같은 origin 사용을 전제로 한다. 외부 origin이 필요하면 해당 고객용 시작 작업 인수에 `--allow-origin`을 추가한다. 이 패키지에 고객 인증서·SSO·방화벽 설정이 자동 포함되지는 않는다.

## 입력 계약

`POST /api/cycle`은 기존 입력에 `observed_at`(시간대 포함 실제 작업 완료 시각), `cycle_id`, `lot_id`, `context`, `demo:false`를 포함한다. `rows`에는 선택된 공정의 센서 입력만 보낸다. `/api/contract`로 입력 계약을 조회한다. 합불·불량 원인 같은 사후 검사 값을 센서 입력에 넣지 않는다.

`POST /api/feedback` 예시:

```json
{"event_id":"cycle-001","outcome":"pass","actor":"inspection-system","evidence":"검사성적서-001","source_id":"inspection-001-revision-1"}
```

`outcome`은 `pass`, `fail`, `unknown` 중 하나다. `source_id`는 검사 기록 고유 ID다. 재전송은 같은 ID·같은 내용으로 하며 정정 검사는 새 revision ID를 사용한다. 위젯의 조사 등록·보류는 학습 정답으로 사용하지 않는다.

`POST /api/lot-close` 예시:

```json
{"process":"pressfit","context":{"machine_id":"M1","part_number":"PART1","program":"P1-v1"},"lot_id":"LOT-001","actor":"MES-adapter"}
```

해당 조건의 LOT에 등록된 모든 실제 작업의 검사 결과가 확정돼야 한다. 종료 후 새 작업을 같은 LOT에 추가할 수 없다. 같은 작업의 정확한 재전송은 가능하다. 다른 조건에서 같은 LOT 이름을 쓰는 것은 분리 관리한다. 작업 시각이 뒤섞여 LOT 구간이 겹치는 경우 학습을 보류한다. 설비·품목·프로그램 변경은 새로운 context로 등록한다.

## 파일 자동 수신

API를 붙이기 어려운 경우 `runtime-state/inbox`에 JSON 파일을 기록한다. 먼저 `.tmp` 파일로 쓰기를 끝낸 후 `.ready.json`으로 이름을 바꾼다. 엔진은 약 60초마다 처리한다. 한 파일은 20 MB 이하, 항목 1~1000개다.

```json
{"format":"milg_inbox_v1","kind":"cycles","items":[{"process":"pressfit","cycle_id":"cycle-001","lot_id":"LOT-001","observed_at":"2026-11-12T09:00:00+09:00","demo":false,"context":{"machine_id":"M1","part_number":"PART1","program":"P1-v1"},"rows":[{"units":{"force":"N","displacement":"mm"},"displacement":[0,1,2,3,4,5,6,7],"force":[0,10,20,30,40,50,60,70]}]}]}
```

위 숫자는 형식 예시이며 실데이터가 아니다. 복사해서 실학습하지 않는다. `kind`를 `feedback`, `lot_close`로 바꾸면 `items`에 각 API 본문을 담는다. 파일명은 `001-cycles.ready.json`, `002-feedback.ready.json`, `003-close.ready.json` 순서를 권장한다. 선행 데이터가 없어 실패한 파일은 다음 점검에서 재시도한다. 부분 입력 후 중단될 수 있으므로 작업 ID와 검사 source ID를 유지한다. 완료 파일은 내용 해시로 재처리를 생략한다. 원본 파일은 임의 삭제하지 않으며 고객의 보관 정책에 따라 정리한다.

## 학습·적용 규칙

- 활성화한 context만 대상으로 한다. 최초 합불 학습은 검사 확정 작업 100건·5개 LOT 이상, 학습 구간 합격/불합격 각 10건, 검증·시험 구간 각 5건 이상이다. 이는 실행 하한이며 현장 성능 보장의 표본 수가 아니다.
- 최초에는 실제 작업 시각순 LOT 60/20/20으로 나눈다. 이후에는 이전 평가 시점보다 뒤의 새로운 LOT 2개·40건 이상을 검증/시험에 배정한다. 이전 시험 결과를 반복적으로 보고 같은 시험 구간을 다시 통과시키지 않는다. 실패·중단된 학습의 시험 LOT도 재사용하지 않는다.
- 특징·표준화는 학습 구간에서 확정한다. MILG 자체 누적 통계 모델, 선형 모델, 비선형 모델을 동일 구간으로 비교한다. 후보 선택과 임계값 결정에는 검증 구간만 사용한다. 최종 시험은 선택된 후보의 승격 판정에 사용한다.
- 기본 승격 하한은 검증·시험 각각 AUC 0.65 이상, 검출률 50% 이상, 정상 오경보율 10% 이하다. 고객 기준에 맞춰 더 엄격하게 설정할 수 있다. 기존 현장 모델이 있으면 같은 새 검증·시험에서 AUC 하락 0.01, 검출률 하락 0.03, 오경보 상승 0.02 이내인지도 확인한다. 첫 현장 모델이 없거나 검사 정정으로 기존 모델이 무효이면 기존 모델과의 유효 비교는 제공되지 않는다.
- 학습 중 정답·설정·배포 모델이 달라지면 적용을 보류한다. 모델 파일과 전처리·임계값·검사 참조를 저장한 후 DB의 적용 포인터를 한 트랜잭션으로 전환한다. 기준 미달 후보는 보고서로 남기고 운영 모델을 교체하지 않는다.
- 감시는 적용 후 생산된 새로운 작업의 검사 결과를 사용한다. 기본 100건·3개 LOT·정상 20건·불량 10건이 쌓이면 AUC/검출률/오경보를 평가한다. 기준 미달, 모델 파일 손상, 학습 정답 정정 시 이전 유효 모델로 복구한다. 이전 모델도 같은 새 구간을 통과하지 못하면 기본 분석으로 복구한다. 정답이 충분하지 않으면 성능 감시는 대기 상태로 표시한다.
- 압입 `normal_reference` 모드는 검사 정상 40건·3개 LOT 이상에서 정상 기준을 생성한다. 정상 기준 이탈과 최종 합불 예측은 별개다. 정상 기준은 데이터 유입만으로 계속 이동시키지 않는다.

## 운영·장애 확인

`/operations`와 인증된 `/api/learning/status`에서 활성 모델, 학습 결과, 대기 사유, 감시 상태, 백업 상태, 적용·복구 기록을 확인한다. 재학습은 별도 프로세스로 실행되며 기본 점검 주기 60초, 후보 재시도 간격 최소 300초, 한 작업 제한 시간 30분이다. OS 파일 잠금으로 같은 저장소의 학습·복구 중복 실행을 막는다. 비정상 중단된 작업은 다음 점검에 interrupted로 기록한다.

`runtime-state/learning-worker.log`, `learning-supervisor.json`을 확인한다. worker 로그는 약 5 MB 기준으로 이전 로그 1개를 보관한다. 학습·추론은 고객 서버 내부에서 이루어진다. Python 서버 실행 중에만 자동 점검한다. 작업 스케줄러를 등록하지 않았다면 창을 닫으면 서버도 종료된다.

정책이 등록되면 하루 한 번 `runtime-state/backups/YYYYMMDD`에 SQLite와 모델을 백업한다. **같은 디스크 백업은 디스크 고장 대비 원격 백업이 아니다.** 고객 보관 경로로 암호화·접근 통제된 사본을 추가해야 한다. 보관 기간은 고객 정책에 맞춰 정하며 엔진은 과거 백업을 자동 삭제하지 않는다. 백업 실패는 점검 결과에 표시된다.

복구 명령은 `python -m mlng_ai.delivery restore --source <백업폴더> --state <새상태폴더>`다. 원본 상태를 덮어쓰지 않는다. 모델 적용 이력과 고객 데이터는 복원되고 API 토큰은 새로 발급된다. 복구본의 후보 자동 학습은 정지 상태로 복원되므로, 원 서버 중지·입력 경로 전환 후 운영자가 다시 활성화한다.

## 고객 협의가 필요한 입력

MILG 설치 담당자는 패키지 설치, 데이터 매핑, 학습 정책, 위젯 연결, 실행 작업, 복구 시험을 수행한다. 고객이 제공·확인할 것은 설비/품목/프로그램 정보, 센서 단위와 작업 경계, 독립 검사 합불 정의·기록, LOT 종료 기준, 설치 PC·망·접근 권한이다. 이 입력 없이 자동으로 고객 데이터베이스의 의미를 알아내거나 모든 공정의 합불을 학습하지 않는다.
